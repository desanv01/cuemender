## R02 — One owner for state, admission and lifecycle

Files: internal/incidents/coordinator.go, app wiring and lifecycle.

- Establish one linearization order for start/stop/check/report/dismiss/result commit, cache install and publication. A small dedicated operation gate or single-owner command loop is sufficient; do not introduce a framework. Never hold that owner across OBS network I/O. Avoid reverse lock order with app.stateMu: status/settings/onChange callbacks cannot run under coordinator state mutex when they acquire app locks.
- Reserve category/job capacity before persistence and roll back reservations on failure. Maintain one actual job per category/two total including canceled-but-not-yet-joined jobs; do not remove admission early then launch overlapping I/O. Concurrent starts return one session and enforce expected revision even on repeat start. Closed coordinator rejects new operations.
- Manual check while monitoring joins/creates the current-session category incident with origin=manual and zero viewer counts; stopped manual check gets separate scope. Dismiss cancels only the target incident/request, never another job of that category.
- Use request/session/revision/provider generation consistently from admission through durable result commit. Revalidate within the serialized commit decision, not before unlocking. Prevent stop/dismiss/settings change/reconnect/new session/newer report being overwritten by an older saved JSON snapshot. Apply ownership guards to manual jobs too. Explicit recheck remains usable after settings changes and gets a new request identity.
- Invalidate/cancel affected jobs on settings/provider change and stop even when only manual work exists. Preserve historical evidence as stale/interrupted with truthful status; never leave orphaned investigating work or relabel old facts as fresh. A joining report updates counters but does not launch another read after an already completed diagnosis; explicit recheck owns refresh.
- Close joins all jobs and incoming commands before store shutdown; no goroutine-per-report or detached context.Background task. Reconcile store-failure state safely and truthfully; repeated stop must not silently return success after failed durable stop. Safety may stop intake immediately, but durable failure must remain visible/retryable.
- Tests: concurrent start/check/report against real SQLite, deterministic pause before result commit then stop/dismiss/settings change/new-session, manual read across generation change, old-incident dismissal during new job, actual app snapshot/SSE while scheduling (lock inversion), whole-app blocked diagnostic shutdown with active HTTP/SSE, port release and DB reopen. Preserve all existing P02 cancellation tests.

## R03 — Atomic durable state and exact bounds

Files: internal/store and coordinator persistence callers.

- Commit vote, feedback totals and incident transition in one transaction. Fault injection must leave no partial vote/count/state; don't let stale snapshots overwrite newer report totals or findings. Use appropriate compare/update or serialized ownership with transactional reads; keep indexed columns and JSON coherent.
- Enforce delivery/message 24-hour expiry using the actual expiry instant and a deterministic time representation/comparison. Keep at most 10,000 retained keys after successful insertion, with deterministic documented eviction and retained duplicates inert. Do not extend duplicate retention merely by retrying. Test exact TTL and boundary insertion, reopen and duplicate variants.
- Test the 10,000 reporter/detail and feedback bounds at/over capacity. Existing actors may replace votes and report without falsely incrementing distinct count; new distinct actors over the bound get honest rejection without partial dedup/count writes.
- Propagate recovery/list/transaction errors instead of treating failed reads as empty history or startup success. Recover all affected active records, not just the first 500 total history entries. Preserve active records while pruning completed history to 500/30 days during a running process as well as restart. Session/history metadata must not grow through an unbounded successful loop unnoticed.
- Keep migration-1 settings intact. Adjust the unaccepted P03 schema/types only as necessary; document compatibility with worker-created migration-2 test data. Do not delete the user's DB or silently downgrade/reset it.
- Tests: migration/reopen; failed incident creation/scheduling/finding/dismiss/stop/vote; DB/cache/private/public snapshots agree; no success acknowledgment/publication on failed commit. Preserve the three new store regressions and add missing exact bound/concurrency cases.
