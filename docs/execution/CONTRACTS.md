# Shared contracts

Revision: 1.1 • Changes require Codex decision and affected-packet review.

This specifies observable behavior and data semantics, not mandatory function names. Introduce structures as consumed; P01 does not implement the full future state machine.

## C01 — Identifiers, time and provenance

- IDs are opaque cryptographically random strings generated by the backend. Use crypto/rand; no extra UUID dependency is required.
- Public incident code: short uppercase alphanumeric code, collision checked. Internal record IDs are not reused as authorization capabilities.
- Persist UTC timestamps; JSON uses RFC3339 with explicit timezone. Durations use time.Duration internally.
- Every asynchronous observation/result carries request_id, monitoring_session_id, config_revision, connection_generation and observed_at as relevant to its source.
- Each connection lifecycle increments its generation on invalidation/replacement. Results from superseded generations are unusable even if received recently.
- Separate mode=live or rehearsal and origin=viewer or manual. Test fixtures cannot acquire live provenance by changing display text.
- Request IDs aid correlation, never authority. Error responses are bounded and sanitized.

## C02 — Settings and startup

Default listen address: 127.0.0.1:8787. Loopback IPv6 is permissible when deliberately configured and covered by tests; 0.0.0.0, empty host and non-loopback addresses are rejected. On port conflict, fail clearly rather than silently changing the OBS overlay URL.

CLI minimum:
- --data-dir PATH: isolate config/database; default os.UserConfigDir()/LiveCheck.
- --listen ADDRESS: explicit override, same validation.
- --no-browser: do not launch a browser; print the one-time local control URL directly to the interactive console.
- --session-only-secrets: explicit memory-only secret storage for this run.
- --version: print version/build metadata and exit without opening a database.
- --mode live|rehearsal is implemented in P05; do not silently accept an unimplemented mode earlier.

config.json holds schema_version, listen_address, twitch_client_id (non-secret), obs_address (default ws://127.0.0.1:4455) and small startup preferences. The initial MVP accepts loopback OBS endpoints only; no arbitrary remote URLs or URL-embedded passwords.

SQLite app_settings holds one versioned expectations record:
- revision, initially 0 if unconfigured; increases transactionally on every saved expectation change.
- microphone: configured=false or InputRef.
- stream_track: null until confirmed; integer 1–6 when configured.
- track_confirmed_at: timestamp of the user's explicit confirmation.
- visual: disabled by default; when enabled, expected scene identity + direct scene_item_id + source identity.
- Revision is supplied with updates; mismatch is 409. No silent lost updates.

InputRef: OBS input name, optional stable input UUID when supported, plus context identity needed for re-resolution. Scene-item ID alone is not globally unique; scope it to its scene and scene collection/session context. P02 records actual SDK support. Renamed/deleted/recreated items require revalidation rather than automatic retargeting.

Partial setup is valid: an unconfigured microphone/track is null/unconfigured, not an invented default. Structural settings validation begins in P01; existence against live OBS begins in P02. Secret-looking fields in config input are rejected; no password/token fields in stored settings.

JSON startup writes are atomic replace with validation. SQLite update is transactional with revision compare. State publishes only after persistence succeeds.

## C03 — HTTP, authentication and browser transport

All routes use the local loopback authority. Validate Host against the actual bound host/port, reject foreign Origin on browser API requests, and disable CORS. Mutations require same-origin Origin, application/json and bounded bodies (default 64 KiB). Use structured input validation; reject unknown fields on mutations.

### Private-session bootstrap

1. On startup generate a 256-bit random one-time launch token, lifetime 5 minutes, held only in memory.
2. Control entry URL: /control/#bootstrap=TOKEN. The fragment is not sent as an HTTP request path/query. Do not put this link into ordinary logs or reports.
3. Static browser JS reads the fragment, clears it with history.replaceState, and POSTs {"token":"..."} to /api/v1/session/bootstrap.
4. Validate Host/Origin/body and token, atomically consume it, issue a separate high-entropy session cookie and CSRF token. Rate-limit invalid attempts.
5. Cookie: HttpOnly, SameSite=Strict, Path=/, no Domain, expires at process exit. Because the supported listener is local HTTP, Secure is not set; no remote-host support is implied.
6. Other state-changing private routes require the session plus X-CSRF-Token. GETs do not mutate product state.
7. Sessions and launch tokens are never persisted. Restart invalidates both. If bootstrap expired before use, restarting is the simple MVP recovery.
8. GET /control/ can serve its static shell unauthenticated; it contains no private data. Without a valid session it displays a locked/relaunch message.
9. A browser reload with a valid cookie obtains its CSRF token through private GET /api/v1/state. Do not place it in public state.

Private responses: Cache-Control: no-store. Add a restrictive self-only CSP suitable for external JS/CSS, Referrer-Policy: no-referrer and nosniff; prevent framing of private controls. No inline scripts, remote analytics or third-party assets. Overlay is intended for OBS and must remain embeddable.

### Response convention

Success JSON: {"data": ... , "request_id":"..."}.
Error JSON: {"error":{"code":"...","message":"safe explanation"},"request_id":"..."}.
400 malformed/invalid; 401 no private session; 403 CSRF/origin/host denied; 404 missing resource; 409 state/revision conflict; 410 expired proposal; 429 cooldown/queue busy; 503 required service unavailable; 500 sanitized internal failure. Do not expose raw SDK errors containing credentials.

### SSE

Event name state; data is a full appropriate projection, carrying monotonic state_revision and mode. Send an initial snapshot, then updates and heartbeat comments (suggested 15 seconds). Browser reconnect receives current state; Last-Event-ID does not imply an event journal or replay.

state_revision is monotonic within one running process; it may reset on process restart. settings.revision is independently persisted. Clients reconnect to the current full snapshot without assuming a durable SSE event sequence. Within an instance, neither cached settings nor a subscriber's sequence may regress because of reordered commits/publications.

Use bounded subscriber buffers; replace/coalesce snapshots or disconnect slow clients. Cancel on request context/shutdown. Reconnect delay is bounded. HTTP shutdown must actively end SSE streams. No sensitive private snapshot may be serialized by a public handler.

### Projection allowlists

Private snapshot may contain connection states, setup readiness, redacted expectations, incident evidence, proposals, pending authorization instruction and history. Never actual Twitch tokens, OBS password or bootstrap token.

Public snapshot schema: mode, state_revision, monitoring_active, service_status, incidents[{public_id, category, stage, message_code, local_verification, feedback_summary}], demo_label when rehearsal. Only stage/category-derived fixed copy or tightly allowlisted message codes. No usernames/user IDs, source names/UUIDs, scene paths, configuration, action preconditions, raw chat, arbitrary error strings or credentials.

P01 has empty incidents, monitoring_active=false and truthful not_connected states. A settings revision can trigger an SSE snapshot without publishing settings. Public service_status is only ready/checking/disconnected/idle; no endpoint details.

## C04 — Twitch and observation adapters

Twitch command normalized fields: delivery_id, message_id, broadcaster_id, actor_id, received_at, command, category or public_incident_id, connection_generation. Retain only command metadata required for the feature, not full chat.

Installed-client authorization uses the broadcaster's own identity: token subject, channel ID and sender ID must match the selected own-channel model. Request user:read:chat and user:write:chat for required outgoing replies, verify current API docs. Credentials stay backend-only. P02 implements validation at startup/hourly, serialized refresh and rotated-token persistence.

Default policies (named constants, adjustable only with documented reason):
- Per-actor issue-command cooldown: 10 seconds.
- Aggregate outgoing replies: at most one per 3 seconds, bounded queue of 20 with expiry; obey stricter Twitch API limits/Retry-After.
- Delivery/message dedup retention: 24 hours, bounded 10,000 entries; document eviction. Repeats while retained do not count twice.
- One active incident per category per monitoring session.
- Reports are processed only while monitoring; !streamhelp can work while connected but idle.
- Ignore own outgoing account messages. Confirmation from a separate viewer is used in live validation.
- Feedback accepted only for current-session open incidents in awaiting_feedback/unresolved after an eligible finding/check; stale/unknown codes do not reopen history.
- Latest feedback per distinct actor replaces that actor's previous vote; duplicate deliveries have no effect.

OBS read result contains source/context identifiers, mute value when known, complete six-track bool map when known, program scene, configured direct item visibility, streaming status, timestamps and connection generation. Missing field/read failure is unknown, never false.

UI observations become stale after 5 seconds by default. Diagnosis reads on demand. A repair always performs a new preflight read with a 5-second deadline; it cannot rely solely on the cached UI snapshot. Record partial errors per field so one failed read does not manufacture a different finding.

## C05 — Findings, incidents and feedback

Finding:
id, incident_id, code, category, evidence_status, explanation_code,
expectation_revision, observation provenance, observed values, manual guidance,
supported_action_kind (null or ADD_MIC_TO_TRACK).

Store typed facts rather than arbitrary model prose. Plain English is rendered from those facts; no runtime model required.

Incident:
internal id, public code, session_id, mode, origin, category, stage, opened_at,
updated_at, report_count, distinct_reporters, findings, local_verification,
feedback counts, closure outcome, closed_at.

Stages and permitted main transitions:
- reported -> investigating
- investigating -> finding_available | no_supported_finding | insufficient_information | interrupted
- finding_available -> awaiting_approval (track mismatch) | awaiting_feedback (manual-only finding)
- awaiting_approval -> applying | expired | invalidated | dismissed
- applying -> awaiting_feedback (read-back matches) | action_unknown | unresolved
- action_unknown -> awaiting_feedback | unresolved | interrupted (read-only reconciliation)
- awaiting_feedback -> unresolved (negative feedback) | closed (explicit broadcaster closure)
- unresolved -> investigating (explicit retry check) | closed | dismissed
- no_supported_finding / insufficient_information / interrupted / expired / invalidated -> investigating on explicit recheck with fresh evidence, or dismissed/closed.
- Terminal closed/dismissed do not accept new feedback or approvals. New reports create a new incident once the prior category incident is terminal.

Positive viewer feedback updates counts; it does not automatically close an incident or erase negative reports. The operator closes with viewer_confirmed only when current positive feedback exists and no current negative feedback; otherwise use unresolved, dismissed, or local_only. Label it as viewer reports, not measured playback truth.

local_verification = not_attempted | verified | failed | unknown. Distinguish local verified from feedback confirmed in every UI path.

Old session work cannot mutate new incidents. Monitoring stop/restart invalidates pending proposals. An in-flight external write cannot be erased by stop: finish/read-only reconcile its record, but do not begin another.

## C06 — Proposal and repair invariants

Proposal binds: id, incident_id, session_id, mode, kind=ADD_MIC_TO_TRACK, input identity, expected complete track map, desired map, selected track, config_revision, connection_generation, created_at, expires_at (60 seconds default), status and one execution action_id.

The browser approves only proposal ID and expected config revision. Never accept input name, track map, command name or arbitrary OBS request from the approval body.

Required sequence:
1. Authenticate local session and CSRF; verify monitoring, live/rehearsal graph, proposal ownership/status/TTL and exact revision.
2. Atomically reserve proposal; second click returns the existing action state and cannot create a second write.
3. Reread source identity and all six assignments under the current generation. Confirm configured track and expectation revision remain unchanged. Any map difference from proposal preconditions invalidates it.
4. If already assigned, record no-op/recheck needed; do not send a write.
5. Compute desired map as fresh map with exactly the selected track enabled.
6. Commit durable action intent and preconditions before the write. Store failure => zero writes.
7. Send the one supported update once for that action.
8. Read back fresh state. Exact desired map => local verified. Mismatch => unresolved, preserving evidence. Missing read/write timeout => unknown, not a false failure/success.
9. Reconcile unknown by fresh reads only. Never blindly replay the mutation after a timeout/reconnect/restart.
10. Further corrective attempts require a new diagnosis/proposal and fresh user approval.

At most one OBS mutation in flight. No auto rollback. Preserve other assignments from the immediate preflight map. OBS does not supply an atomic compare-and-set here: an independent OBS client or human may change state between read and write. Document this limitation and detect disagreement by read-back; do not promise impossible prevention of all external races.

P04 action statuses: proposed/reserved, intent_recorded, write_sent, verified, failed, unknown, no_op, invalidated. Durable recovery treats an unfinished intent as potentially written even if write_sent was not persisted. Restart never resumes a write; it invalidates approval and schedules read-only reconciliation.

## C07 — Persistence, retention and secret lifetime

- schema_migrations: unique integer version, applied_at.
- app_settings: singleton expectations JSON or normalized equivalent, revision, updated_at; compare-and-update transaction.
- P03 tables persist incident identity/state, minimal reports, typed findings and bounded dedup IDs.
- P04 action record stores proposal/preconditions/desired map, intent time, last observed map, status and reconciliation notes. Action IDs are unique.
- Foreign keys enabled per connection; transactions enforce related writes. A conservative serialized SQLite connection configuration is sufficient.
- Required retention policy: keep at most 500 completed incidents or 30 days, whichever removes earlier; preserve active incidents and unresolved action records until reconciled/dismissed with recorded outcome. Bound dedup separately. Clear-history cannot remove pending/uncertain action audit needed for recovery.
- Data-directory lock prevents two application instances using the same DB; never automatically delete a lock held by another process. P01 may acquire an exclusive loopback listener first for the same configured port; P06 must address same-data/different-port processes explicitly.
- Secrets interface: Get/Set/Delete with context and typed not_found/unavailable errors; values must not accidentally stringify into logs.
- Store refreshed token pair as one credential entry to avoid torn pair updates. If saving rotation fails, mark session persistence degraded; no plaintext fallback.
- OS keyring unavailable: show needs_attention and require an explicit choice of memory-only mode. Foundation may run with credential features disabled.
- Remove application-owned test keys on completion. Never enumerate unrelated user credentials.
- Shutdown flushes state and closes transports/DB. Browser sessions expire; secrets persist only if keyring mode was selected.
